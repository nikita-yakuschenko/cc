Ты работаешь как senior full-stack разработчик и системный архитектор. Нужно спроектировать и реализовать внутренний корпоративный сервис Авангард Строй для создания коротких брендированных ссылок и UTM-разметки.

## Контекст продукта

Сервис используется сотрудниками компании внутри закрытого корпоративного контура.

Публичные короткие ссылки должны иметь домен:

https://go.avgst.ru

Основные форматы:

https://go.avgst.ru/project/a8K3p
https://go.avgst.ru/vacancy/H7d92
https://go.avgst.ru/promo/Q4mN8
https://go.avgst.ru/v83kjaz

Категория ссылки необязательна.

Если категория выбрана:

https://go.avgst.ru/{category}/{code}

Если категория не выбрана:

https://go.avgst.ru/{code}

Примеры категорий:

* project — проект дома;
* vacancy — вакансия;
* promo — рекламная акция;
* event — мероприятие;
* document — документ или презентация;
* catalog — каталог;
* offer — коммерческое предложение.

Категории должны храниться в управляемом справочнике. Пользователь не должен вводить категорию произвольно.

## Основная задача сервиса

Сервис должен позволять:

1. Вставить исходную ссылку.
2. Выбрать, нужна ли UTM-разметка.
3. При необходимости создать UTM-разметку через конструктор.
4. Выбрать тематику ссылки.
5. Сгенерировать короткую ссылку.
6. Скопировать короткую ссылку.
7. Сгенерировать QR-код.
8. Просматривать ранее созданные ссылки.
9. Отключать и редактировать ссылки.
10. Изменять адрес назначения без изменения короткой ссылки.
11. Просматривать базовую статистику переходов.

## Пользовательский сценарий

### Шаг 1. Исходная ссылка

Пользователь вставляет URL.

Система должна:

* проверить корректность URL;
* разрешать только http и https;
* извлечь существующие query-параметры;
* определить наличие UTM-меток;
* показать домен и страницу назначения;
* предупредить, если ссылка уже содержит UTM-разметку.

Если UTM-метки уже существуют, предложить:

* сохранить существующую разметку;
* изменить разметку;
* удалить разметку.

Нельзя добавлять повторяющиеся utm-параметры.

### Шаг 2. Выбор сценария

Пользователь выбирает один вариант:

* Просто сократить ссылку.
* Добавить UTM-метки и сократить.

Если UTM-разметка не нужна, пользователь сразу переходит к выбору категории и созданию короткой ссылки.

Если UTM-разметка нужна, открывается конструктор UTM.

### Шаг 3. Конструктор UTM

Обязательные поля:

* utm_source — источник;
* utm_medium — канал;
* utm_campaign — кампания.

Необязательные поля:

* utm_content — содержание объявления;
* utm_term — ключевое слово.

Необходимо хранить UTM-параметры отдельно в базе, а не только в составе итогового URL.

Предусмотреть управляемые справочники для utm_source и utm_medium.

Примеры utm_source:

* vk;
* yandex;
* telegram;
* email;
* avito;
* 2gis;
* partner;
* offline.

Примеры utm_medium:

* cpc;
* social;
* email;
* messenger;
* referral;
* display;
* qr;
* offline.

Пользователь должен видеть понятные русские названия, но в URL должны попадать нормализованные технические значения.

Например:

Источник: ВКонтакте
Значение: vk

Канал: Платная реклама
Значение: cpc

Все UTM-значения должны нормализоваться:

* нижний регистр;
* пробелы заменяются на подчёркивания;
* удаляются лишние символы;
* сохраняется предсказуемый формат.

Показывать пользователю итоговую длинную ссылку до её сокращения.

Пример:

https://avgst.ru/projects/modul-120?utm_source=vk&utm_medium=cpc&utm_campaign=summer_houses_2026&utm_content=carousel_project_120

### Шаг 4. Категория и код

Пользователь выбирает категорию из справочника либо вариант «Без категории».

Короткий код генерируется автоматически.

Использовать безопасный набор символов без неоднозначных знаков:

abcdefghijkmnopqrstuvwxyz
ABCDEFGHJKLMNPQRSTUVWXYZ
23456789

Не использовать:

* 0;
* O;
* I;
* l;
* 1.

Для категорийных ссылок по умолчанию использовать код длиной 5 символов.

Для ссылок без категории использовать код длиной 7 символов.

Примеры:

https://go.avgst.ru/project/a8K3p
https://go.avgst.ru/v83kjaz

Предусмотреть возможность вручную указать пользовательский алиас, но:

* только латинские буквы;
* цифры;
* дефис;
* длина от 3 до 64 символов;
* регистр не должен влиять на уникальность;
* необходимо проверять занятость алиаса.

Зарезервировать системные пути:

* admin;
* api;
* login;
* auth;
* health;
* docs;
* qr;
* stats;
* settings.

## Редиректы

Публичные маршруты:

GET /{code}
GET /{category}/{code}

Алгоритм:

1. Найти активную ссылку.
2. Проверить срок действия.
3. Проверить категорию, если она присутствует.
4. Записать событие перехода.
5. Выполнить HTTP-редирект на итоговый URL назначения.

Для обычных управляемых ссылок использовать временный редирект 302 или 307, чтобы адрес назначения можно было менять без проблем с кешированием.

Не выполнять редирект на:

* javascript:;
* data:;
* file:;
* локальные адреса;
* localhost;
* 127.0.0.1;
* внутренние приватные IP-диапазоны;
* некорректные URL.

## Развёртывание через Dokploy

Production-развёртывание приложения выполняется через **Dokploy** с использованием `docker-compose.yml`.

Приложение и PostgreSQL должны быть развёрнуты в рамках одного проекта Dokploy, но как два независимых сервиса с раздельным жизненным циклом.

### Целевая схема развёртывания

В проекте Dokploy необходимо создать:

1. Compose-сервис приложения.
2. Отдельный сервис PostgreSQL, развёрнутый средствами Dokploy.

PostgreSQL не должен запускаться внутри `docker-compose.yml` приложения.

Compose-файл приложения должен содержать только сервис самого приложения и дополнительные вспомогательные сервисы, если их необходимость появится в дальнейшем.

База данных должна сохраняться независимо от:

* пересборки приложения;
* перезапуска контейнера приложения;
* обновления версии приложения;
* удаления и повторного создания Compose-сервиса приложения.

Не добавлять PostgreSQL в Compose-файл приложения без отдельного архитектурного решения.

### Сетевая схема

Приложение подключается к PostgreSQL через внутреннюю сеть Dokploy.

Для подключения необходимо использовать:

* внутреннее сетевое имя PostgreSQL;
* внутренний порт PostgreSQL `5432`;
* отдельного пользователя базы данных;
* отдельную базу данных приложения.

Не использовать в production:

```text
localhost
127.0.0.1
host.docker.internal
```

Порт PostgreSQL не должен публиковаться во внешнюю сеть без отдельной необходимости.

Публичный доступ к приложению осуществляется через reverse proxy Dokploy.

Публичный домен:

```text
https://go.avgst.ru
```

Приложение внутри контейнера должно слушать:

```text
0.0.0.0:3330
```

Внутренний порт контейнера:

```text
3330
```

Dokploy должен направлять запросы домена `go.avgst.ru` на внутренний порт приложения `3330`.

HTTPS и выпуск SSL-сертификата выполняются средствами Dokploy.

### Требования к Docker-сборке

Необходимо подготовить:

* production-ready `Dockerfile`;
* `docker-compose.yml`;
* `.dockerignore`;
* `.env.example`;
* production entrypoint;
* health-check приложения;
* документацию по развёртыванию в Dokploy.

Docker-образ должен использовать multi-stage сборку.

Production-контейнер должен:

* содержать только необходимые runtime-зависимости;
* запускаться не от пользователя `root`;
* корректно обрабатывать сигналы завершения процесса;
* не содержать исходные секреты;
* не содержать development-зависимости без необходимости;
* запускать Next.js в standalone-режиме;
* слушать порт `3330`.

В конфигурации Next.js необходимо включить:

```ts
const nextConfig = {
  output: "standalone",
};

export default nextConfig;
```

В production-образе необходимо задать:

```dockerfile
ENV NODE_ENV=production
ENV HOSTNAME=0.0.0.0
ENV PORT=3330

EXPOSE 3330
```

Запуск standalone-сервера:

```text
node server.js
```

Не использовать порт `3000` в:

* `Dockerfile`;
* `docker-compose.yml`;
* health-check;
* документации;
* конфигурации Dokploy;
* production-переменных окружения.

Во всех production-конфигурациях порт приложения должен быть равен `3330`.

### Docker Compose

Подготовить `docker-compose.yml`, пригодный для развёртывания в Dokploy.

Ориентировочная структура:

```yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile

    restart: unless-stopped

    environment:
      NODE_ENV: production
      HOSTNAME: 0.0.0.0
      PORT: 3330

      DATABASE_URL: ${DATABASE_URL}

      APP_URL: ${APP_URL}
      NEXT_PUBLIC_APP_URL: ${NEXT_PUBLIC_APP_URL}

      AUTH_SECRET: ${AUTH_SECRET}

    expose:
      - "3330"

    healthcheck:
      test:
        [
          "CMD",
          "wget",
          "--no-verbose",
          "--tries=1",
          "--spider",
          "http://127.0.0.1:3330/api/health"
        ]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 30s
```

Это ориентир, а не требование слепо копировать конфигурацию. Итоговый Compose-файл необходимо адаптировать к реальной структуре проекта и production-образа.

Не добавлять устаревшее поле:

```yaml
version:
```

Не использовать `ports`, если Dokploy может маршрутизировать трафик на контейнер через `expose`.

При необходимости публикации порта для локальной разработки создать отдельный файл:

```text
docker-compose.local.yml
```

Production-конфигурация Dokploy не должна без необходимости публиковать порт `3330` непосредственно на хосте.

### Подключение к PostgreSQL

Строка подключения передаётся приложению через переменную окружения:

```text
DATABASE_URL
```

Формат:

```text
postgresql://USER:PASSWORD@POSTGRES_HOST:5432/DATABASE_NAME?schema=public
```

Где:

* `USER` — пользователь PostgreSQL;
* `PASSWORD` — пароль пользователя;
* `POSTGRES_HOST` — внутреннее сетевое имя PostgreSQL в Dokploy;
* `DATABASE_NAME` — имя базы данных приложения.

Реальные реквизиты базы запрещено хранить:

* в Git;
* в `Dockerfile`;
* в `docker-compose.yml`;
* в `.env.example`;
* в исходном коде;
* в клиентском JavaScript;
* в публичной документации.

Секретные значения задаются через Environment Variables в интерфейсе Dokploy.

Необходимо документировать:

* имя PostgreSQL-сервиса;
* внутренний hostname;
* имя базы;
* имя пользователя;
* способ формирования `DATABASE_URL`;
* способ проверки сетевого подключения из контейнера приложения.

### Переменные окружения

Минимальный набор production-переменных:

```env
NODE_ENV=production

HOSTNAME=0.0.0.0
PORT=3330

DATABASE_URL=

APP_URL=https://go.avgst.ru
NEXT_PUBLIC_APP_URL=https://go.avgst.ru

AUTH_SECRET=
```

Также необходимо добавить переменные выбранного механизма авторизации и внешних интеграций.

В `.env.example` для каждой переменной указать:

* назначение;
* обязательность;
* допустимый формат;
* безопасный пример без реальных секретов.

Переменные, доступные браузеру, могут иметь префикс `NEXT_PUBLIC_`.

Секретные значения не должны использовать префикс `NEXT_PUBLIC_`.

### Prisma и миграции базы данных

Для применения миграций в production использовать:

```text
npx prisma migrate deploy
```

Не использовать в production:

```text
npx prisma migrate dev
```

Не заменять production-миграции командой:

```text
npx prisma db push
```

без отдельного обоснованного решения.

Для первой версии, в которой запускается один экземпляр приложения, допускается entrypoint следующего вида:

```sh
#!/bin/sh
set -e

npx prisma migrate deploy
exec node server.js
```

Entrypoint должен:

1. Завершать запуск при ошибке миграции.
2. Не скрывать ошибку подключения к PostgreSQL.
3. Передавать сигналы основному Node.js-процессу через `exec`.
4. Не выполнять development-команды.
5. Не создавать демонстрационные данные при каждом запуске.

Ограничение этого подхода необходимо явно описать: при горизонтальном масштабировании несколько контейнеров не должны одновременно выполнять миграции.

При появлении нескольких реплик следует перенести миграции в отдельный deployment-шаг или одноразовый migration-job.

Seed-данные справочников должны добавляться:

* идемпотентно;
* отдельной командой;
* только при первичном развёртывании или по явному запросу администратора.

### Health-check

Создать endpoint:

```text
GET /api/health
```

Health-check должен проверять:

* что приложение запущено;
* что приложение может установить соединение с PostgreSQL;
* что основной процесс способен обрабатывать HTTP-запросы.

Успешный ответ:

```json
{
  "status": "ok"
}
```

HTTP-статус:

```text
200 OK
```

При недоступности PostgreSQL возвращать:

```json
{
  "status": "unavailable"
}
```

HTTP-статус:

```text
503 Service Unavailable
```

Health-check не должен раскрывать:

* `DATABASE_URL`;
* пароли;
* внутренние hostname;
* IP-адреса;
* SQL-запросы;
* stack trace;
* подробный текст внутренних исключений.

Для проверки соединения использовать минимальный безопасный запрос к базе данных.

Health-check должен быть доступен внутри контейнера по адресу:

```text
http://127.0.0.1:3330/api/health
```

### Домены и маршрутизация

Основной публичный домен:

```text
go.avgst.ru
```

В Dokploy необходимо настроить:

* привязку домена к Compose-сервису приложения;
* внутренний порт назначения `3330`;
* автоматический HTTPS;
* перенаправление HTTP на HTTPS;
* корректную передачу заголовков reverse proxy;
* сохранение исходного IP и протокола в доверенных proxy-заголовках, если это требуется аналитике.

Публичные короткие ссылки должны работать по адресам:

```text
https://go.avgst.ru/{code}
https://go.avgst.ru/{category}/{code}
```

Административная часть может работать на том же домене, например:

```text
https://go.avgst.ru/admin
```

Системные пути должны иметь приоритет над публичными маршрутами коротких ссылок.

### Логирование

Приложение должно писать логи в стандартные потоки контейнера:

```text
stdout
stderr
```

Не хранить основные production-логи только внутри файловой системы контейнера.

В логах запрещено выводить:

* пароли;
* токены;
* cookies;
* `DATABASE_URL`;
* полные заголовки авторизации;
* персональные данные без необходимости.

Для критических ошибок лог должен содержать достаточный технический контекст, но не раскрывать секреты.

### Хранение данных

Постоянные бизнес-данные должны храниться в PostgreSQL.

Контейнер приложения необходимо считать stateless.

Не хранить важные данные только:

* в файловой системе контейнера;
* в директории сборки Next.js;
* во временных файлах;
* в памяти процесса.

QR-коды по возможности генерировать динамически либо сохранять в отдельном постоянном хранилище, если такое требование появится позднее.

Перезапуск или пересоздание контейнера приложения не должен приводить к потере ссылок, UTM-разметки, пользователей или статистики.

### Резервное копирование PostgreSQL

Так как PostgreSQL развёрнут как отдельный сервис Dokploy, резервное копирование базы настраивается отдельно от приложения.

В документации необходимо описать:

* где хранится persistent volume PostgreSQL;
* как создаются резервные копии;
* куда они выгружаются;
* с какой периодичностью выполняется копирование;
* какой срок хранения используется;
* как проверить целостность резервной копии;
* как выполнить тестовое восстановление;
* как сделать ручной экспорт перед опасной миграцией;
* как восстановить базу после сбоя.

Не реализовывать самописную систему резервного копирования внутри Next.js-приложения.

Перед миграциями, изменяющими или удаляющими данные, необходимо предусмотреть создание актуальной резервной копии.

### Обновление приложения

Обновление должно выполняться без пересоздания PostgreSQL.

Базовый порядок обновления:

1. Получить новую версию исходного кода.
2. Собрать новый Docker-образ.
3. Запустить production-миграции.
4. Запустить новый контейнер приложения.
5. Проверить `/api/health`.
6. Проверить авторизацию.
7. Проверить создание короткой ссылки.
8. Проверить публичный редирект.
9. Проверить запись статистики перехода.

При неуспешном health-check новая версия не должна считаться успешно развёрнутой.

Необходимо документировать порядок отката приложения на предыдущий Docker-образ.

Откат кода не всегда означает возможность отката структуры базы, поэтому миграции должны проектироваться с учётом обратной совместимости.

### Критерии готовности развёртывания

Развёртывание считается подготовленным, если можно:

1. Развернуть PostgreSQL отдельно в проекте Dokploy.
2. Подключить приложение к PostgreSQL через внутреннюю сеть.
3. Передать приложению `DATABASE_URL` через Dokploy.
4. Собрать приложение через production `Dockerfile`.
5. Запустить приложение через `docker-compose.yml`.
6. Запустить Next.js на `0.0.0.0:3330`.
7. Выполнить `prisma migrate deploy`.
8. Получить ответ `200 OK` от `/api/health`.
9. Открыть `https://go.avgst.ru`.
10. Авторизоваться в административной части.
11. Создать короткую ссылку.
12. Перейти по короткой ссылке и получить корректный редирект.
13. Зафиксировать событие перехода в PostgreSQL.
14. Перезапустить контейнер приложения без потери данных.
15. Обновить приложение без пересоздания PostgreSQL.
16. Откатить приложение на предыдущий Docker-образ.
17. Создать резервную копию PostgreSQL.
18. Восстановить PostgreSQL из резервной копии в тестовом окружении.
